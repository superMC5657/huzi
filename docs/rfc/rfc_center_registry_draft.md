# RFC: 中心仓库 / 校验和 / 自动升级（草案，未冻结）

> 状态：草案（Draft，未实现、未冻结）。日期：2026-09-26。
> 来源：`docs/undo/BACKLOG.md` §C 包生态（从未启动，产品决策前置）。
> 范围：只做决策前置，不写代码、不改行为。落地本文件即算 BACKLOG-C 的 RFC 步骤完成，执行另估。
> 必读现状：`docs/STATUS.md:90`、`:71`，`docs/USAGE.md` §6（包管理章节）。

## 1. 背景与冲突

现状（已冻结行为，不动）：

- `huzi.toml` + `VersionReq` 范围解析（`1.2.3` 精确 / `^` / `~` / `>=,<` 范围 / `*`、`1.*`）+ 逐包最高满足求解（`select_max_satisfying`，多约束取交集）。
- 传递依赖合并进同一闭包求解；同一包多约束无共同满足版本时直接报错退出（菱形依赖 `test/pkg/app_diamond`），不做自动升级。
- `huzc fetch` 按求解结果落盘 `vendor/<pkg>/<version>/` 并清理落选版本子目录，同时写 `huzi.lock`（逐包精确版本，按包名排序）；`huzc build` 先做同一求解检查，锁存在时必须精确一致（漂移/缺失/多余均报错提示重 `fetch`），无锁时仅做闭包与 `vendor` 检查。
- 模块解析顺序：显式 `path` → 工程 `vendor/` → `vendor/` → 全局缓存 `~/.huzi/packages/`（见 `huzc/crates/huzc/src/pkg/resolve.rs`）；版本子目录内按降序优先试最高版本。
- 自举标准库（`huzi-src`）开箱即用，`import std.* / alloc.* / core.*` 无需在 `[dependencies]` 声明（`USAGE.md` §6 末）。

冲突点：

- `STATUS.md:90` 写的是“包管理无中心仓库、无下载校验和、无 semver 自动升级（求解只选最高满足版，不改写清单）”，`USAGE.md:145` 同样写“明确不做”。
- 只要这两行不动，任何中心仓库/校验和/自动升级的设计或实现都与快照自相矛盾。
- 因此本 RFC 的前置动作是**先改 STATUS 措辞**（见 §7），把“明确不做”降级为“当前快照不做，草案在途”。不做这一步，后续一切免谈。

## 2. 目标与非目标

IN（本草案回答什么）：

- 信任模型选型（校验和放哪、谁签名、离线怎么验）。
- 命名空间规则（扁平名是否保留、作用域名形式、与 `std/core/alloc` 保留前缀的关系）。
- 版本消解语义：是否保留“只选最高满足、不改写清单”，自动升级以什么显式命令形态存在。
- 离线 `vendor/` 在引入仓库后的定位（构建输入唯一性、网络边界、缓存优先级）。
- STATUS/USAGE 措辞补丁提案（先改措辞，再谈实现）。

- 仓库服务端 API、索引格式、发布/撤包（yank）流程、账号权限。
- 具体校验和算法选型之外的实现细节（§3 只给推荐默认值）。
- 任何代码改动、`huzc` 新子命令的 CLI 最终形态、`huzi.toml`/`huzi.lock` 字段的最终 schema。

## 3. 信任模型（提案）

现状：零信任。`path`/`vendor`/全局缓存均无校验，拿到什么编什么。`huzi.lock` 只记 `(name, version)`，无哈希（见 `test/pkg/app*/huzi.lock` 现状）。

威胁模型（最小诚实集）：

1. 传输篡改（镜像/代理投毒）。
2. 注册表内容事后篡改（同一版本号内容被换）。
3. 依赖混淆（同名包在不同来源解析到不同内容）。

提案（v1 最小可用，不自建 PKI）：

- `huzi.lock` 新增每包校验和字段（推荐 `sha256`，对包内容规范归一化后哈希；归一化规则留执行 RFC 定，至少固定文件排序 + 换行符 + 权限位无关）。
- 注册表索引经 HTTPS 分发即可，v1 不做独立索引签名；包 tarball 哈希由注册表生成，客户端在 `fetch` 落盘 `vendor/` 前必验，失败硬报错、无静默回退。
- `build` 是纯离线命令：只读 `huzi.toml` + `huzi.lock` + `vendor/`，校验 `vendor` 内容哈希与锁一致（已落盘被手改也算漂移，报错提示重 `fetch`）。
- 来源锁定：`huzi.lock` 记录每包来源（`path` 本地 / `registry` + 注册表 URL / 版本）；同名包在 `path` 显式声明与仓库来源冲突时，显式 `path` 优先但必须在 lock 中标记，`build` 按 lock 重放，不做隐式切换。
- 不做的：首次信任 TOFU pin、自签名包上传（v1 只信任注册表哈希，不接受发布者自带签名作为校验依据；发布者身份只做命名空间归属，不做构建时验签）。

开放问题：私有 registry URL 白名单、离线环境下哈希缺失旧锁的迁移（建议：旧锁无哈希时 `fetch` 补写、`build` 告警而非报错，过渡期一个版本）。

## 4. 命名空间（提案）

现状：扁平包名（`my_math`），`vendor/<pkg>/<version>/` 即命名空间。`std/core/alloc` 是语言保留前缀，走编译器内置解析，不进包解析。

问题：引入中心仓库后扁平名必然撞名/抢注/仿冒（`std-json` vs `json` 类）。

提案：

- 保留扁平名解析（兼容现有 `huzi.toml`/fixtures），注册表侧引入可选作用域：`scope/name`（如 `acme/json`）。无作用域包与现有行为一致；有作用域包在 `huzi.toml` 中写全名，落盘仍为 `vendor/<scope>__<name>/<version>/` 或 `vendor/<scope>/<name>/<version>/`（二选一，执行 RFC 定；推荐后者，可读且避免转义纠纷）。
- `std`、`core`、`alloc` 永久保留，注册表拒绝注册这三个顶级名及 `std/*` 前缀；`import std.*` 永远走内置标准库，不走包解析（延续 `USAGE.md` §6 末规则）。
- 抢注政策本草案不定，只定机制：作用域内包名唯一，作用域首次认领；无作用域老包在仓库上线时按“先到先得 + 异议期”冻结（细节留执行 RFC）。

## 5. 版本消解：是否保留“只选最高满足、不改写清单”（提案：默认不变，升级显式化）

现状语义（冻结）：`fetch`/`build` 共用同一求解——全部约束交集内取最高满足版；冲突直接报错；绝不改写 `huzi.toml`；`huzi.lock` 是求解结果的精确快照。

本草案回答标题问题：**默认语义不改**。理由：可复现性优先；自动升级是货架上最容易悄悄破坏构建的东西；当前“冲突报错”行为已有负例锁定（`app_diamond`），改默认等于改契约。

提案（两档语义）：

- 默认档（不变）：`fetch`/`build` 只按已有约束选最高满足版，不改写 `huzi.toml`。`build` 有锁必严校验（现状行为保留）。
- 显式升级档（新增，命令名待定）：`huzc update [<pkg>]` 或 `huzc fetch --upgrade`，允许在约束内（或经确认放宽约束后）重选新版，并**同步重写 `huzi.lock`**，如放宽了约束则同步改写 `huzi.toml` 的对应 `version` 串并打印 diff。绝不允许 `build` 隐式升级——`build` 永远是校验器，不是求解器。
- `update` 的求解算法与 `fetch` 同一函数（复用 `select_max_satisfying`），区别只在输入约束是否允许被重写；重写必须显式、逐包、可审计。

反例（明确不采纳）：`build` 自动放宽约束找共同版本（如菱形 `1.0.0` vs `2.0.0` 自动升到 `2.x` 交集）——这会把今天的编译期冲突错误变成静默语义变更，不接受。

## 6. 离线 `vendor/` 定位（提案）

原则：**引入仓库后，`vendor/` 仍是唯一构建输入；网络只属于 `fetch`/`update`**。

- `build` 永不联网。缺 `vendor` 落盘时保持现状行为：报错提示先 `fetch`，不自动拉取。
- `fetch` 是唯一联网命令；新增 `--offline`（只用 `vendor/` + 全局缓存求解，联网即错）与 `--frozen`（要求 `huzi.lock` 存在且完全一致，不做重求解，行为等价今天有锁的 `build` 校验，但用于 CI 前置检查）。两 flag 语义抄 `cargo --offline/--frozen`，不发明新词。
- 缓存优先级（联网 `fetch` 时）：注册表 → 全局缓存 `~/.huzi/packages/`（命中且哈希一致则免下载）→ 落盘 `vendor/`；`build`/模块解析时优先级反过来：`vendor/` 优先于全局缓存（构建可复现，缓存只是下载加速）。注意现状 `resolve.rs` 在版本子目录内降序试最高版本——引入锁后模块解析应以锁选定版本为准，而非目录降序，执行时须收敛这两处（草案只指出，不改代码）。
- `vendor/` 是否进 git：两种都支持。提交派得完全离线构建；忽略派靠 `huzi.lock` + 全局缓存重放。文档只给建议（应用仓建议提交，库仓建议忽略），不强制。
- 落选版本清理：保留现状（`fetch` 清理该包下落选版本子目录），避免 `vendor` 膨胀；如需多版本共存（`app_multi` 类场景是单包多版本候选、非共存），执行 RFC 另议。

## 8. 开放问题（留给执行 RFC）

1. 索引格式与发布流程（`huzc publish` 要不要、包内容规范、yank 语义、版本号不可变性）。
2. 校验和算法与目录归一化（本草案推荐 sha256，归一化规则未定）。
3. 预发布版本（`1.0.0-alpha`）是否进入 `VersionReq`（现状 `SemVersion::parse` 拒绝非纯数字分量，连带影响仓库版本接纳）。
4. `huzi.lock` schema 扩展（`checksum` + `source` 字段名、旧锁迁移期行为）。
5. 私有源与多源优先级、离线镜像（vendor 打包导出/导入）形态。
6. `update` 的交互细节（是否改 `huzi.toml` 约束串、是否支持 `--dry-run` 打印升级矩阵）。
